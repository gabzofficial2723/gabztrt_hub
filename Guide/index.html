Open the project and make a safe edit

Open the whole ProjectPort folder in VS Code, not just one file. That keeps the file tree visible and makes relative asset paths easier to understand.

  1. Open the folder.

    In VS Code, choose File → Open Folder… and select ProjectPort. Find files in the Explorer on the left.

  2. Choose the matching page and file.

    Words usually live in an HTML file. Appearance usually lives in CSS. Clicks and other behavior usually live in JavaScript.

  3. Make a small change and save it.

    Press Ctrl+S (Windows) after editing. Save before refreshing the browser.

  4. Preview and check your work.

    Open HTML/index.html in a browser to preview the main site, then try the relevant buttons and a narrow/mobile window.

  5. Review the changed files.

    Use VS Code's Source Control view or git status before sending anything to GitHub.

Good first edit Change one paragraph in HTML/index.html, save it, refresh the page, and confirm the new words appear. Then try a CSS color change and undo it with Ctrl+Z.
3

HTML: edit the words and page structure

HTML tags describe what each piece is: a heading, paragraph, image, link, button, or section.

Change text

In the matching HTML page, replace the words between the opening and closing tags. Keep the tags themselves.

<h2>About Me</h2>
<p>Write your new paragraph here.</p>

Change a link

The destination is the href. A link such as #projects jumps to an element whose id is projects.

<a href="#projects">See projects</a>
<section id="projects">...</section>
Keep names paired If a link uses href="#contact", the page needs an element with id="contact". A class can be reused on many elements; an id should identify one unique element on that page.
What should I edit on each page?
  • Home: text, navigation, About, My Works cards, contact details, and the project preview dialog are in HTML/index.html.
  • Profile: replace the template name, role, intro, skills, experience, project names, and contact prompts in HTML/profile.html.
  • Bunny Vault: its page structure and button/dialog placeholders are in HTML/bunny.html. The gallery itself is built by JAVA/bunny.js.
  • Page title and icon: edit the <title> or favicon link near the top of the relevant HTML file.

CSS: change how the site looks

A CSS selector finds an element; the declarations inside its braces change its appearance.

.project-card {
    padding: 24px;
    border-radius: 20px;
    background-color: #e3f0d6;
}

Which stylesheet?

CSS/style.css is the main site's styles. CSS/profile.css and CSS/bunny.css add styles for their own pages. CSS/fonts.css defines custom fonts.

Match the selector

.project-card targets the class class="project-card". #about targets the unique id="about". A missing dot or hash means a different selector.

Common style changes
  • Color: change color for text or background/background-color for a surface.
  • Spacing: adjust padding inside an element or margin outside it.
  • Size: adjust font-size, width, height, or max-width.
  • Roundness: adjust border-radius.
  • Phone layout: find the @media rules near the bottom of the stylesheet; these styles apply at smaller screen widths.
Start with the existing rule Search the CSS file for the class name you see in the HTML. Change its existing rule before adding a new one so you do not accidentally create two conflicting styles.

Trace an interaction safely

  1. Find the button/link in the page HTML and note its class, id, and accessible label.
  2. Search for that class or ID in the corresponding JavaScript file.
  3. Read the whole nearby handler and any helper it calls before editing.
  4. Keep the HTML hook and JavaScript selector in sync; test mouse, keyboard, open, and close states.

Keep data separate from behavior

The project preview copy is grouped in projectPreviewTemplates; slider content is grouped in gameplayClips. Edit the data object when only words, links, or colors change. Change the event-handler code only when the behavior itself needs to change.

Bunny Vault data and backups IndexedDB stores folder/settings records and saved directory handles; uploaded images are written to the selected local folder. Clearing browser site data, moving the folder, or revoking permission can affect access. Back up the actual ProjectPort folder and important photos independently.

Alternatives and an easier way to build

Choose the simplest tool that fits the feature. ProjectPort is currently a static site, so most updates need only HTML, CSS, JavaScript, and a browser refresh—no framework or build command.

DecisionCurrent approachAlternativeWhen to choose the alternative
Page layoutCSS Grid for project/profile/card layouts; Flexbox for one-dimensional rows and controls.Use Flexbox for everything, or fixed-position blocks.Prefer Grid for rows and columns; Flexbox for a single row/column. Fixed positioning is best for overlays, not the normal page layout.
Responsive sizingrem, percentages, viewport units, min(), and clamp() with breakpoints.Hard-code pixel widths/heights everywhere.Fixed pixels are useful for icons, borders, and deliberate minimums. Use flexible widths and clamp() for page gutters, type, and layouts that must adapt.
SpacingExisting padding, margin, and gaps are tuned per component.Define a small spacing scale, such as 8 / 12 / 16 / 24 / 32px, as CSS variables.A scale is easier when redesigning many pages at once. For a small edit, adjust the existing component rule instead of introducing a new system.
Project popupsNative <dialog> with showModal(), built-in modal behavior, and custom animation.A hand-built <div> overlay.Use a custom overlay only if the design needs behavior the native dialog cannot provide; then you must build focus management, Escape handling, background inertness, and accessibility yourself.
Repeated project contentSemantic HTML cards plus a JavaScript template object keyed by project title.Hard-code every popup's content in separate markup, or generate every card from JS.Separate static markup is fine for a few unique pieces. A data array is easier for a long, repeated list. Avoid generating content with JS unless it is genuinely dynamic.
Gameplay visualsOne externally hosted animated GIF at a time; it avoids embedding video players.Static image, MP4/WebM video, or a video platform embed.Use a static image for lowest bandwidth; a compressed MP4/WebM for longer clips and playback controls; an embed when platform playback/attribution matters. Animated GIFs can still be large and cannot offer normal video controls.
Browser storageLocalStorage for a tiny font preference; IndexedDB for Vault records; selected local folder for image files.Keep everything only in memory, use downloadable files, or use a server/database.Memory resets on refresh; download/export is simple for one-off data; a server is needed for accounts or cross-device syncing. Do not put secrets in frontend storage.
Site architecturePlain static HTML/CSS/JS pages.Framework, component library, package manager, and build pipeline.Stay static while pages are manageable and interactions are limited. Consider a framework only when shared components, data-driven screens, routing, or team scale make the extra setup worthwhile.

A repeatable, low-friction build process

  1. Write the page outline before styling.

    List the sections and the content each one needs. Use semantic HTML such as header, nav, main, section, article, and footer.

  2. Build one representative component.

    Finish one project card, creator card, or profile card first. Then duplicate its HTML for similar content and keep the class names consistent.

  3. Style from the outside inward.

    Set page width and section spacing first, then grid/flex layout, then card padding, typography, colors, borders, and decorative effects. Prefer editing the existing selector.

  4. Make it flexible before polishing.

    Use Grid/Flexbox, minmax(0, 1fr), max-width, and clamp(). Test at desktop, tablet, and phone widths; add a media query only when the layout actually needs to change.

  5. Add behavior only after the control exists.

    Use real buttons for actions and links for navigation. Add one event listener or delegated handler, make its state visible, and provide keyboard and error states.

  6. Test one change at a time.

    Save, refresh, test the exact feature, check the browser Console, then inspect the narrow layout. Review the Git diff before committing.

Small habits that save time

  • Use VS Code search (Ctrl+Shift+F) for a class, ID, or visible text.
  • Keep repeated values in CSS custom properties when they genuinely share a purpose.
  • Use descriptive image filenames, meaningful alt text, and paths relative to the file using them.
  • Use browser DevTools' element inspector to test spacing before permanently editing CSS.
  • Prefer one clear source of truth for repeated data; avoid copying the same JS logic into multiple handlers.
  • Keep page content in HTML, visual rules in CSS, and interaction/data updates in JavaScript.

Add or rename a My Works project

A project card's title connects its HTML to its preview template in JavaScript. Keep the title exactly the same in both places.

  1. In HTML/index.html, copy one existing <article class="project-card"> inside .project-grid.
  2. Change the card's <h3> title and short description.
  3. Give the eye button a matching accessible name, such as aria-label="Preview Garden Planner".
  4. In JAVA/script.js, add a template under projectPreviewTemplates with the exact same title.
  5. Save both files, refresh the home page, and test that card's eye button and close actions.

Edit the Game Enthusiast favorite-channel list
  • In HTML/index.html, find .project-creators. Each .creator-card is one channel.
  • Change the avatar image's src, card heading, YouTube icon link's href, short description, and subscriber/date values in its <dl>.
  • The subscriber values are rounded snapshots, not live data. The current set was checked November 14, 2026; update the displayed count and note when you refresh them.
  • To add someone, duplicate one .creator-card and replace its details. The grid will arrange the new card automatically.
  • To change a gameplay GIF, edit the gameplayClips list in JAVA/script.js. Each entry has a creator name, image description, GIF URL, Tenor source-page URL, and accent color. The carousel loads only the active GIF image; it does not create video players.

  • The section is shown only when the project title is exactly Game Enthusiast. If you rename that project, update the matching condition in JAVA/script.js.
  • For visual changes, edit .gameplay-slider and .creator-card in CSS/style.css. Each creator card class has light/dark gradient colors and an emboss shadow you can adjust separately.

Replace pictures, backgrounds, and fonts

Put new files in the matching assets folder, then update the path where the image or font is used.

assets/bg assets/fonts assets/models assets/pictures assets/pictures/thumbnails 
<img src="../assets/pictures/my-photo.jpg"
     alt="A short description of the photo">

HTML files are inside HTML/, so ../assets/ means “go up one folder, then into assets.” CSS files are inside CSS/, so their asset URLs also commonly start with ../assets/.

  • Use the actual file name, including its extension, such as .jpg, .png, .svg, or .mp4.
  • Match capitalization exactly; web hosts may treat Photo.jpg and photo.jpg as different files.
  • Write useful alt text for meaningful images. Use alt="" for purely decorative images.
  • To add a new custom font, add its font-face definition in CSS/fonts.css and point it to the font file in assets/fonts/.

Preview changes and fix common issues

This is a static HTML/CSS/JavaScript site. For ordinary text and style edits, save the files and refresh the page; no compile step is currently needed.

  1. Open the page you changed.

    Home: HTML/index.html. Profile: HTML/profile.html. Bunny Vault: HTML/bunny.html.

  2. Try the interaction you edited.

    Click the buttons, follow the links, and open/close dialogs. For layout edits, also test a narrow browser window.

  3. Look for errors.

    In a desktop browser, press F12 and select Console if a script stops working. A missing image usually means its path or spelling is wrong.

  4. Refresh cached files if necessary.

    If an older style or script still appears, check the page's ?v= number in its stylesheet/script link and increase it, then refresh again.

Quick troubleshooting guide
  • Image is broken: verify the exact file name and the relative path from the HTML/CSS file.
  • CSS did not change: check that you edited the stylesheet linked by that page, then refresh or increase its cache version.
  • Button stopped working: check the browser Console for spelling errors and make sure the element's class/ID matches the JavaScript selector.
  • In-page link goes nowhere: compare its href="#..." to the destination element's id.
  • Vault cannot select a folder: use a browser that supports the File System Access API and grant permission when prompted.
Cache versions in this project The home page currently uses version numbers in its CSS and JavaScript links. When a browser keeps an old copy, increase the relevant ?v= number in that page's HTML. This does not change the file name.

Save your changes to the GitHub repository

Editing and saving changes your local files. A Git commit records a checkpoint; pushing sends committed work to GitHub.

SaveCtrl+S in VS Code
ReviewCheck the changed files
CommitName your checkpoint
PushSend it to GitHub
Option A: use VS Code Source Control
  1. Save your edits with Ctrl+S.
  2. Open Source Control from the left toolbar, or press Ctrl+Shift+G.
  3. Review the files listed under Changes. Click a file to inspect its diff before staging it.
  4. Stage only the files you intend to keep by clicking the + beside each file (or stage all after reviewing the list).
  5. Enter a short commit message, such as Update project descriptions, then select Commit.
  6. Select Sync Changes or Push to send the commit to GitHub. Sign in if VS Code asks.
Option B: use Git in the VS Code terminal

Open Terminal → New Terminal in VS Code. The terminal must be inside the ProjectPort folder. These commands show the full manual path from your saved files to this repository's GitHub branch:

git status
git branch --show-current
git remote -v
git diff
git add -- "Guide\index.html" "HTML\index.html" "CSS\style.css" "JAVA\script.js"
git diff --cached
git commit -m "Update portfolio site and owner guide"
git push origin master
  1. git status lists changed and untracked files. Confirm the list contains only work you intend to publish.
  2. git branch --show-current prints the branch name. This checkout currently uses master; substitute the printed name in the push command if yours differs.
  3. git remote -v shows where origin points. Confirm it is gabzofficial2723/gabztrt_hub before pushing.
  4. git diff reviews edits to already tracked files. New files appear as untracked in git status; they appear in the staged diff after you add them.
  5. git add -- ... stages only the listed files. Replace the sample paths with the files you actually changed. To stage a different group, edit the path list—avoid staging unrelated work.
  6. git diff --cached shows exactly what will go into the next commit. If anything is unexpected, unstage that file with git restore --staged "path\to\file", edit the file, and review again.
  7. git commit -m "..." saves a named checkpoint locally. git push origin master sends that branch's commits to GitHub.
For your next update This repository already tracks origin/master, so after you edit, stage, and commit, git push is enough. Use git push -u origin master only when setting an upstream for a branch for the first time.
Sync the latest GitHub version before editing

When your working tree is clean, run this before starting a new round of edits:

git status
git pull --rebase origin master

This brings down the latest master commits and places your local commits on top. If Git reports conflicts, resolve the marked sections, save the files, run git add -- "path\to\resolved-file", then continue with git rebase --continue. If you are unsure, stop and ask for help—do not use a force push to get around a conflict.

If Git says your name or email is not configured, set the name and the email associated with your GitHub account with git config --global user.name "Your Name" and git config --global user.email "you@example.com". If authentication is requested, complete the GitHub sign-in prompt; never paste a password or access token into a source file or commit.

Repository update is not always website publishing A successful push updates GitHub. The public website updates too only if hosting/deployment (for example GitHub Pages) is configured for this repository and branch.
